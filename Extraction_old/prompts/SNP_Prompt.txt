E. HIERARCHY FLATTENING (PARENT->CHILD PREFIXING)
Goal: convert indentation/grouping into colon-prefixed flat labels.
Maintain a PREFIX STACK based on hierarchy.
IMPORTANT -- HOW INDENTATION IS PROVIDED TO YOU:
The PDF text you receive has been pre-processed to PRESERVE visual indentation.
Each row label is prefixed with spaces proportional to its indent level in the PDF.
The number of leading spaces depends on the specific PDF's column layout. Treat
indentation RELATIVELY: a line with MORE spaces than the previous stack entry is
a child; EQUAL spaces means same level (sibling or pop); FEWER spaces means ancestor.
The space legend for this specific Clark County SNP is:
2 spaces  = level 1  (sub-group headers and root data rows:
"Unrestricted assets", "Restricted assets",
"Bond bank receivable, current",
"Capital assets not being depreciated", etc.)
4 spaces  = level 2  (child headers and child data rows:
"  Cash and investments", "  Accounts receivable",
"  Interest receivable", etc.)
6 spaces  = level 3  (grandchild data rows:
"    In custody of the County Treasurer",
"    With fiscal agent",
"    Investments with fiscal agent")
8 spaces  = total/subtotal rows (e.g. "        Total assets")
NOTE: The minimum indent level in the data area may be 2 spaces, not 0.
Do NOT assume 0 spaces = root. Use RELATIVE depth: the shallowest indent
you encounter in the data rows is your root level (level 1).
USE LEADING SPACES AS THE SOLE HIERARCHY SIGNAL.
NEVER use label semantics to infer hierarchy. The word content of a label
is irrelevant to its indent level. Always trust the space count.

DASH-ONLY ROWS: CLASSIFY AS TYPE A (GROUP HEADER), NOT TYPE C (DATA ROW)
CRITICAL RULE: A row whose ONLY value token is a single dash "-" (with no
other numeric values) is a GROUP HEADER (TYPE A), NOT a data row.
Rationale: In government financial statements, section sub-headers like
"Restricted assets -" and "Cash and investments -" print a decorative dash
in the total column to indicate "this is a header, not a sum." The dash is
NOT a real value. These rows have no actual numeric data.
Detection: If the only token(s) on the line are dashes (one "-" per column
or a single "-"), treat the row as TYPE A regardless of the dash presence.
Specifically: if ALL extracted value tokens are "-" with no numeric values,
the row is TYPE A.
Examples from this PDF:
"  Restricted assets  -"           <- dash only -> TYPE A (push to stack)
"    Cash and investments  -"      <- dash only -> TYPE A (push to stack)
These must NOT be emitted as data rows.

LINE CLASSIFICATION (based on leading spaces + presence of NUMERIC values):
TYPE A (Group Header):
A line with NO numeric values -- either completely blank of values,
OR containing only dash "-" tokens with no actual numbers.
Action:
Do NOT emit a row.
Push { indent_level: <space_count / 2>, label: <this label> } onto the PREFIX STACK.
If this line's indent_level <= current stack top's indent_level:
FIRST pop all stack entries with indent_level >= this line's indent_level,
THEN push this new entry.
TYPE B (Child Data Row):
A line WITH at least one numeric value (not just dashes) whose indent level
is STRICTLY GREATER THAN the deepest entry currently on the PREFIX STACK.
Action:
Emit a row:
Row Items = stack[0].label + ": " + stack[1].label + ": " + ... + ": " + this_label
(join ALL current stack entries with ": ", then append this label)
Do NOT pop the stack -- siblings at the same indent level share the same parent.
TYPE C (Sibling/Ancestor Data Row or Total Row):
A line WITH at least one numeric value whose indent level is LESS THAN OR
EQUAL TO the deepest entry currently on the PREFIX STACK.
OR any line whose label begins with "Total".
Action:
STEP 1: Pop all stack entries whose indent_level >= this line's indent_level.
STEP 2: Emit the row using whatever shallower entries remain on the stack
as prefix (or no prefix if stack is empty).
STEP 3: If this is a CP "Total" row, CLEAR the entire PREFIX STACK.

PREFIX STACK RULES (CRITICAL):
SIBLING RULE: Processing one sibling row at indent level N does NOT pop the
parent at level N-1. The parent stays on the stack for all subsequent siblings.
Only a row at indent level <= N-1 triggers a pop of the N-1 entry.
SAME-LEVEL POP RULE (the most commonly misapplied rule):
When a DATA ROW appears at indent_level == stack_top.indent_level:
-> This row is a SIBLING of the stack top, NOT a child.
-> Pop the stack top first (it and this row share the same parent).
-> Then emit using the remaining shallower stack entries as prefix.
"Equal indent level" always means POP, never means "keep as parent."
NO SEMANTIC OVERRIDES: Never pop or keep stack entries based on label
wording. Even if a label contains the same word as the stack top
(e.g., "Investments with fiscal agent" when parent is "Cash and investments"),
DO NOT pop the parent based on word similarity. The indent level is the
ONLY trigger for popping.

G1) EXTRACT VALUES
DASH GLYPH NORMALIZATION (CRITICAL -- RUN BEFORE ALL OTHER STEPS):
Treat ALL of the following as equivalent dash cell tokens:
U+002D  -   (hyphen-minus)
U+2010  -   (hyphen)
U+2013  --  (en dash)
U+2014  --- (em dash)
U+2012      (figure dash)
U+FE58      (small em dash)
When a PDF extractor drops or skips one of these characters, it creates
a MISSING CELL, not a missing value. Treat it as "-" and preserve it
as a real column slot -- do NOT collapse surrounding tokens to fill the gap.
If the extracted token count for a row is LESS than N, and the row label
is known to have dash cells (from visual inspection or column arithmetic),
insert "-" at the gap position before assigning tokens to columns.
BLANK CELL vs DROPPED DASH DISTINCTION (CRITICAL):
A PDF table cell can be empty in two different ways:
TYPE 1 — PRINTED DASH:
The PDF contains an actual dash character (-, –, —, etc.) at that
cell position. Your extractor may or may not capture it.
Rule: treat as a "-" token. Already covered by DASH GLYPH
NORMALIZATION above.
TYPE 2 — EMPTY CELL (no character printed):
The PDF contains NO character at that cell position. The cell is
visually blank or shows whitespace only. The extractor produces
nothing for this cell — not even a dash.
Rule: this still counts as a real column slot that must receive "-"
in the output. It is NOT a signal to pack surrounding tokens left.
CONSEQUENCE — THE ONLY RELIABLE SIGNAL IS TOKEN COUNT vs N:
If extracted token count for a row = N:
All N cells had a value (numeric or dash). Assign left-to-right.
If extracted token count for a row < N:
One or more cells were TYPE 2 empty (no character at all).
You CANNOT tell which cells are empty from the token stream alone.
You MUST use the GROUP STRUCTURE RULE below to determine placement.
Never assume the gap is at the right end.
Never pack tokens into the leftmost slots.
DASH TOKEN PRESERVATION (CRITICAL):
Treat any dash glyph as a real cell token.
If multiple dash cells appear in a row, you MUST preserve each dash as a
separate token.
Never collapse "--" into one "-" token.
Never drop dash tokens during extraction.
DASH-NEGATIVE FUSION PREVENTION (CRITICAL):
A standalone dash token that appears as its own spaced column cell is ALWAYS
an independent cell token -- NEVER a negative sign prefix for the value
that follows it.
A dash and the next numeric/parenthesized value are TWO separate tokens if
and only if horizontal whitespace (column gap) exists between them in the
layout-preserved extraction.
A dash immediately adjacent (no space) to a value with no column gap is a
negative sign, not a cell: e.g. "-(507,846)" with no gap = one token "(507,846)".
When in doubt, treat the dash as its own cell token (preserve, do not fuse).
ZERO-VALUE ROW PRESERVATION (CRITICAL):
A row where ALL columns are blank/empty in the PDF is a REAL DATA ROW.
It must be emitted with "-" in every reporting column.
Never skip it, never merge it with adjacent rows, never use its
absence as a reason to shift tokens from the next row upward.
Detection rule: If a row label is present in the text but ZERO numeric
tokens follow it before the next row label, treat it as an all-dash row:

Emit the row with "-" in every column.
Do NOT assign any tokens from the following row to this row.
Do NOT advance the token stream for this row.

This applies even if the row has no dash glyphs printed — the absence
of any value in the PDF is itself evidence that all columns = "-".
Valid cell tokens are:

numeric with commas: 1,234 or 12,345,678
parenthesized negatives: (1,234)
dash cell: -
Ignore "$" signs.

Fix broken parentheses:
"5,232)" -> "(5,232)", "(5,232" -> "(5,232)".
NO ADDEND SWAP RULE -- CRITICAL:
When the statement has columns:
Governmental Activities | Business-Type Activities | Total | Component Unit ...
The first numeric token after the row label belongs to Governmental Activities.
The second numeric token belongs to Business-Type Activities.
The third numeric token belongs to Total.
The fourth numeric token belongs to Component Unit.
If token count = N, never swap token 1 and token 2.
Even if both arrangements satisfy the Total column, the original token order
must be preserved.
ABSOLUTE ADDEND ORDER LOCK -- CRITICAL:
If a data row has exactly N extracted value tokens and the SUM column value
already equals the sum of the ADDEND columns, then the row is considered valid.
In that case:
- DO NOT reorder values between ADDEND columns.
- DO NOT swap Governmental Activities and Business-Type Activities.
- DO NOT move any value from one ADDEND column to another.
- DO NOT use arithmetic to improve or reinterpret the row.
- Preserve the original left-to-right token order exactly.
Arithmetic validation may confirm a row, but it must never be used to reorder
values when the token count is already complete.
This rule overrides all G3 repair rules.

G2) COLUMN ASSIGNMENT -- POSITION-FIRST (CRITICAL)
INDEPENDENT COLUMN ABSOLUTE TOKEN-ORDER LOCK:
Columns to the RIGHT of the SUM ("Total") column are INDEPENDENT — they
have no arithmetic relationship to each other or to the SUM column.
For ALL independent columns (every component unit column):
- Assign tokens STRICTLY in left-to-right order, one token per column slot.
- NEVER swap a '-' and a numeric token between adjacent independent columns,
regardless of domain knowledge about which entity "should" have a value.
- If token count = N, output exactly as-is. Zero exceptions.
ARITHMETIC SELF-CHECK (run after all rows are assigned):
For every independent column, sum all its DP row values and compare to its
CP "Total" row value. If they do NOT match for any independent column, a
left-shift error occurred on at least one row. Identify that row (it will
be a row where the next column has a value but this column shows '-' in the
CP total reconciliation), restore the '-' to this column, and shift the
numeric value one slot right.
The single most important rule: assign tokens using their horizontal PDF
position, not by packing them left-to-right sequentially.
Every statement has a fixed column schema detected in Section C.
Each token must be assigned to the column whose horizontal position it occupies.
POSITION-FIRST ASSIGNMENT STEPS:

For each token in the row, determine its horizontal character position
from the layout-preserved text extraction.
Map that position to the correct column using the column position ranges
established from the header block and confirmed by normal data rows.
If a column position contains no token (blank or gap in layout), assign
"-" to that column -- do NOT slide other tokens left to fill the gap.
Never re-order or re-pack tokens to fill empty columns from the left.

TRAILING INDEPENDENT COLUMN DASH-DROP RECOVERY (CRITICAL — ADD TO G2):

PROBLEM PATTERN:
In government SNP statements, the rightmost independent columns (component
unit columns) frequently have a printed dash "-" at x-positions near the
RIGHT EDGE of their column zone. PDF extractors routinely DROP these
trailing-edge dashes because:
  1. The dash sits at the boundary between two column zones.
  2. Right-aligned dashes render at the far right of a narrow column,
     where the extractor's word-boundary detection fails.
  3. The extractor produces N-1 tokens instead of N.

When this happens and the parser uses sequential left-to-right packing,
the LAST token (which belongs to Col6/last independent column) gets
assigned to Col(N-1) instead, and Col(N) incorrectly gets "-".

DETECTION RULE (run for every row where token count < N):
STEP 1 — MAP EACH TOKEN TO ITS COLUMN BY x0 POSITION:
  For each extracted token T, check its x0 coordinate against the
  known column x-ranges (established from the header block).
  Assign T to the column whose x-range contains T.x0.

STEP 2 — IDENTIFY EMPTY COLUMN SLOTS:
  Any column whose x-range contains NO token is a gap.
  Record gap position(s).

STEP 3 — INSERT "-" AT EACH GAP POSITION:
  For each gap column C (in left-to-right order):
    Insert "-" at position C.
    Shift all tokens originally assigned to columns >= C one slot right.
  Result: exactly N tokens, one per column.

STEP 4 — VERIFY WITH ARITHMETIC SELF-CHECK (G3.3):
  After full section assignment, sum each independent column's DP rows.
  Compare to that column's CP total value.
  If mismatch: a gap was inserted at the wrong position.
  Re-examine the affected row(s) and correct gap placement.

COLUMN x-RANGE ESTABLISHMENT (ONE-TIME, AT STATEMENT START):
  During header block parsing (Rule C1), record the x0 and x1 of
  each column header word. Define column zones as:
    Col[i].x_min = midpoint(Col[i-1].x1, Col[i].x0)   [or 0 for Col1]
    Col[i].x_max = midpoint(Col[i].x1, Col[i+1].x0)   [or page_width for ColN]
  Lock these ranges for the entire statement. Never recompute per-row.

SPECIFIC CASE — RIGHTMOST COLUMN DASH DROP:
  The most common case is Col(N) (last independent column) having its
  dash dropped. Detection is simple:
    - Token count = N-1
    - Last token's x0 falls within Col(N-1)'s x-range, NOT Col(N)
    - No token exists with x0 in Col(N)'s x-range
  Fix: assign last token to Col(N-1), insert "-" at Col(N).
  DO NOT move last token to Col(N) — it belongs where its x0 says.

  Col5 x-range: ~465–510   Col6 x-range: ~510–560
  Row "Nonexpendable permanent endowments":
    Extracted tokens: '-'(x=261), '-'(x=309), '-'(x=367), '-'(x=437),
                      '-'(x=496), '1,015,586'(x=524)
    x=496 → Col5 zone → Col5 = '-'   ✓
    x=524 → Col6 zone → Col6 = '1,015,586'   ✓

  IF extractor drops the x=496 dash:
    Extracted tokens: '-'(x=261), '-'(x=309), '-'(x=367), '-'(x=437),

    Map by x0: x=524 → Col6 zone.
    Gap detected at Col5 (no token in ~465–510 range).

G2-SPLIT) TWO-PAGE TABLE MERGING -- Y-COORDINATE ROW CLUSTERING (y_tol <= 3.5)
SPARSE COLUMN ANTI-SHIFT (CRITICAL):
When a column has values on only SOME rows (sparse column), the
extractor may produce fewer tokens than N for those rows where
the sparse column is blank.
For every row where extracted token count < N:

Identify WHICH columns are likely blank by checking horizontal
position of each extracted token against known column positions.
Do NOT pack tokens sequentially left-to-right to fill N slots.
Insert "-" at each column position that has no token at its
expected horizontal x-coordinate.
Only after gap-filling should you verify the SUM column.

Specifically: if a right-hand component unit column (e.g., Industrial
Development Authority) is blank for a given row, insert "-" at that
column's position. Never pull the NEXT row's value upward.
Run this BEFORE G2A whenever the statement spans two physical pages where:
Page 1 = row labels + primary government columns
Page 2 = component unit columns only (no row labels)
CLUSTERING RULE (apply identically to BOTH pages):
Sort all words on the page by (top, x0) -- vertical position first,
then horizontal.
Group words into rows using a running average top:
- Start a new row group with the first word.
- For each subsequent word W:
If |W.top - current_row_avg_top| <= 3.5 pt:
Add W to the current row group.
Recompute current_row_avg_top = average of all tops in group.
Else:
Close the current row group.
Start a new row group with W.
Each resulting row group = one logical table row.
Record avg_top for every group (used for cross-page matching in Step 3).
STEP 1 -- CLUSTER PAGE 1 INTO ROWS:
Apply the clustering rule above to all Page 1 words.
For each resulting row group, record:
{
row_index  : sequential integer starting at 1,
avg_top    : running-average vertical position of the group,
row_label  : the label string extracted from this group,
p1_tokens  : ordered list of numeric tokens (include "-" for dashes)
}
ALL-DASH ROWS ARE REAL ROWS:
If a row group produces only dash/blank tokens for all primary
government columns, it still has a valid avg_top and row_index.
Register it. Never skip, collapse, or merge it with adjacent rows.
STEP 2 -- CLUSTER PAGE 2 INTO VALUE GROUPS:
Apply the IDENTICAL clustering rule to all Page 2 words.
For each resulting group, record:
{
group_index : sequential integer starting at 1,
avg_top     : running-average vertical position of the group,
p2_tokens   : ordered list of numeric tokens (include "-" for dashes)
}
ALL-DASH GROUPS AND PHYSICALLY BLANK ROWS — THREE CATEGORIES:
CATEGORY 1 — PRINTED DASHES:
The PDF contains dash characters at every column position for this row.
The extractor captures them. The group has avg_top and p2_tokens = ["-","-",...].
Action: Register normally. Include in count. Match in Step 3.
CATEGORY 2 — PRINTED BLANKS (empty cells, no character):
The PDF has no character at any column position for this row.
The extractor captures SOME dashes (from columns that do print dashes)
but the group still has a valid avg_top and appears in clustering.
Action: Register normally. Include in count. Match in Step 3.
CATEGORY 3 — PHYSICALLY ABSENT ROW:
The PDF renders NO characters whatsoever for this row on Page 2
(not even dashes). The extractor produces ZERO words for this row.
No group is created. avg_top gap analysis is the ONLY detection method.
Action: Insert synthetic group per STEP 2B. Include in count.
CRITICAL: Category 3 rows are the most dangerous because they are
invisible to the extractor. Every two-page statement MUST be checked
for Category 3 rows using STEP 2B before proceeding to Step 3.
STEP 2B -- PAGE 2 ROW COUNT INTEGRITY PRE-CHECK (RUN BEFORE STEP 3):
After clustering Page 2 into groups, verify:
count(Page 2 groups) MUST equal count(Page 1 data rows).
If Page 2 has FEWER groups than Page 1 rows:
A physically blank row (no characters printed, not even dashes)
exists on Page 2. It was never rendered and therefore produces
NO words for the extractor to cluster.
DETECTION METHOD -- USE avg_top GAP ANALYSIS:
  Sort all Page 2 groups by avg_top ascending.
  Compute the gap between each consecutive pair of groups.
  Compute the median gap (typical row spacing).
  Any gap > 1.8x the median gap indicates a missing group at
  that vertical position.

INSERTION RULE:
  Insert a synthetic all-dash group at avg_top =
    (prev_group.avg_top + next_group.avg_top) / 2
  with p2_tokens = ["-", "-", ...] (one "-" per component unit column).

IDENTITY RULE -- WHICH ROW IS MISSING:
  After insertion, re-run avg_top proximity matching (Step 3).
  The inserted group will match the P1 row whose avg_top is
  closest to the inserted synthetic avg_top.

ARITHMETIC CONFIRMATION (MANDATORY):
  After full assignment, verify that the component unit total row
  equals the sum of its component unit detail rows.
  If the total does not match, a missing blank row is still present.
  Re-run gap detection until totals reconcile.
STEP 3 TIEBREAKER:
If two P1 rows R1 and R2 are equidistant from P2 group G:
Assign G to the P1 row with the LOWER row_index (earlier in document).
The later row gets the next closest unassigned P2 group.
STEP 3 -- MATCH PAGE 2 GROUPS TO PAGE 1 ROWS BY avg_top:
For each Page 1 row R (in row_index order):
Find the unassigned Page 2 group G where
|R.avg_top - G.avg_top| is minimized.
Assign G.p2_tokens to row R as its component unit column values.
Mark G as consumed (one group -> one row, no reuse).
If no Page 2 group remains within a reasonable proximity of row R:
Assign "-" to all component unit columns for row R.
NEVER assign Page 2 groups by sequential index alone.
NEVER skip a Page 1 row because its p1_tokens are all dashes.
STEP 4 -- ROW COUNT INTEGRITY CHECK:
After Step 3:
count(Page 1 rows) MUST equal count(Page 2 groups consumed).
If Page 2 has FEWER groups than Page 1 rows:
Remaining unmatched Page 1 rows get "-" for all component columns.
If Page 2 has MORE groups than Page 1 rows:
An all-dash Page 1 row was lost in Step 1 -- restore it and re-run
from Step 1. Never discard unmatched Page 2 groups.
To detect missing rows: a gap in avg_top between consecutive Page 1
rows that is larger than 2x the typical row spacing (~13-15 pt)
indicates a missing row at that position. Insert it and re-run.
KEY RULE -- BLANK GROUPS THAT MUST NOT BE SKIPPED:
Any Page 2 group where all values are "-" is still a REAL GROUP
with a valid avg_top. It must be registered in Step 2 and matched
in Step 3. Skipping any blank group shifts ALL subsequent rows
upward by one, producing wrong output.

G2A) ELIMINATION ROW DETECTION -- RUNS BEFORE ANY REPAIR
PRE-CHECK -- DROPPED DASH RECOVERY:
Before running elimination row detection, verify token count.
If extracted token count < N:
1. Compute what the missing column(s) should be using SUM logic:
- If SUM column value equals one of the extracted tokens,
that token belongs in an ADDEND column, not the SUM column.
- Insert "-" at the column position(s) where no token was extracted.
2. Re-run token assignment with the corrected token list.
3. THEN proceed to G2A Step 1.
Specifically for elimination rows:
If you see exactly one positive value P and one negative value N
where |P| = |N|, and token count < N columns:
- The missing token is "-" (a dropped dash cell).
- The SUM column MUST be "-" (since P + N = 0).
- Insert "-" at the gap to restore correct column count before assigning.
STEP 1 -- ASSIGN BY TOKEN ORDER, PRESERVING GAPS:
For an elimination row, assign tokens strictly by their order of appearance
in the extracted text, left to right, one token per column:
Token 1 -> Col1 (first addend column)
Token 2 -> Col2 (second addend column)
Token 3 -> Col3
Token 4 -> Col4
... and so on up to N columns.
Do NOT skip columns. Do NOT pack. Each token fills the next column slot
in sequence exactly as it appears.
STEP 2 -- CONFIRM ELIMINATION PATTERN:
After token-order assignment, verify that:
- At least one ADDEND column contains a positive value P.
- At least one ADDEND column contains its exact negative (P * -1).
- The sum of all ADDEND columns equals 0.
If these conditions are met, this is a confirmed elimination row.
Proceed to Step 3. Otherwise treat as a normal DP row and apply G3.
STEP 3 -- VERIFY SUM COLUMN:
After token-order assignment, the SUM column Col[S] must contain "-".
If it does not (a numeric value landed there), that numeric value is a
shift error -- move it to the rightmost addend column that is "-" and
set Col[S] = "-".
STEP 4 -- OUTPUT AND SKIP G3:
Output the row as assigned. Skip all G3 repair rules for this row.
The addend values cancel (sum = 0) and Col[S] = "-". This is correct.
CRITICAL: Never move either of the two cancelling values into Col[S].
Never compute Col[S] = 0 and output "0". Col[S] must always be "-"
for elimination rows.

G3) ALIGNMENT REPAIR USING SUM LOGIC
Run G3 repair ONLY if one of the following is true:

extracted token count is LESS than N, or
extracted token count is GREATER than N, or
SUM column does not equal the sum of ADDEND columns, or
a dash cell was visibly dropped, or
a value is clearly positioned under the wrong horizontal column.

DO NOT run G3 repair if:

token count equals N, AND
SUM column equals the sum of ADDEND columns, AND
values are already assigned in left-to-right token order.
In that case, output the row as-is.

G3.0 CONTRA-ADDEND / ELIMINATION REPAIR -- RUN FIRST:
This rule fixes rows where one addend is positive and another addend is the
exact negative, but the negative value was incorrectly placed in the SUM column.
If ALL of the following are true:
- SUM column Col[S] contains a numeric value Z, not "-".
- At least one ADDEND column is "-".
- At least one other ADDEND column contains numeric value Y.
- Y + Z = 0 (Z is the exact opposite of Y).
- No independent column needs Z based on right-side positioning.
Then this is a SHIFT ERROR:
- Move Z from Col[S] into the RIGHTMOST ADDEND column that is currently "-".
- Set Col[S] = "-".
- Do NOT recompute Col[S] as a numeric value.
- Do NOT move Z to an independent column.
- This row is an elimination/contra-addend row, so the SUM column must
remain "-".
G3.1 ZERO-SUM SAFEGUARD:
After G3.0, compute:
expected = sum(all ADDEND column values, treating "-" as 0).
If expected == 0:
- Col[S] must be "-".
- If Col[S] contains "0", replace it with "-".
- If Col[S] contains any numeric value, it is a shift error.
Move it to the RIGHTMOST ADDEND column that is currently "-",
then set Col[S] = "-".
- Do NOT move this numeric value to an independent column unless all
ADDEND columns are already non-dash and the value is clearly positioned
under an independent column.
ZERO-SUM ADDEND EXCEPTION (DO NOT REPAIR):
If ALL of the following are true:
- All ADDEND columns already contain non-dash numeric values.
- Those addend values happen to sum to 0 (e.g., equal and opposite).
- Col[S] already contains "-".
- The independent columns (if any) contain their own valid values.
Then the row is already correct. Do NOT apply any G3 repair.
Output the row as-is.
G3.2 NORMAL SUM VERIFICATION:
If expected != 0:
- If Col[S] equals expected:
Keep as-is.
- If Col[S] is "-" and all INDEPENDENT columns are "-":
Set Col[S] = formatted(expected).
- If Col[S] has numeric value Z and Z does not equal expected:
Before moving Z to an independent column, check:
If any ADDEND column is "-" AND Z is needed to make the addends
sum correctly, move Z to the RIGHTMOST empty ADDEND column and
recompute expected.
Only if Z cannot belong to an ADDEND column, move Z to the FIRST
independent column that is currently "-".
Then set Col[S] = formatted(expected).
- If Col[S] is "-" and an independent column contains value Z where
Z equals expected:
Move Z into Col[S].
Set that independent column = "-".
- If there is exactly ONE non-dash numeric token in the entire row:
Use horizontal PDF position if available.
If positioned in addend area, place it in the matching ADDEND column
and compute SUM.
If positioned in independent area, place it in the RIGHTMOST matching
independent column.
Do not guess solely by arithmetic.
G3.3 MANDATORY TOTAL RECONCILIATION (ALL COLUMNS INCLUDING INDEPENDENT):
After all rows in a section are assigned, for EVERY column (including
independent/component unit columns):
Compute: sum of all DP row values in that column for the section.
Compare to: the CP "Total" row value for that column.
If they do not match:
1. Identify which DP row is the likely cause (wrong value assigned).
2. Re-examine that row's Page 2 group assignment using avg_top.
3. Check whether a missing blank P2 group caused a one-row shift
for all subsequent rows in that column.
4. Correct the assignment and re-verify.
NEVER output a JSON where a CP total row does not equal the sum of
its DP rows for any column, unless the statement itself contains
an arithmetic error (rare -- flag it in COA Datapoint as a note).
G4) No duplication:
Each PDF value can exist in only one column.
G5) DPG rows:
All values must be null (not "-").

K2) SAME-DATAPOINT DISAMBIGUATION (CRITICAL)
Some COA Datapoints (e.g. "Other Receivable") appear in both current and
noncurrent contexts within the same Assets section. When a CP membership
table references such a datapoint, use POSITION to disambiguate:

  - For "Total current assets":
    Include only DP rows with that datapoint appearing BEFORE the
    "Total current assets" CP row in the section.

  - For "Total noncurrent assets":
    Include only DP rows with that datapoint appearing AFTER the
    "Total current assets" CP row (or after "Total capital assets"
    if that exists).

  General rule: a DP row belongs to the nearest CP row that follows it
  in the same section whose membership table includes its COA Datapoint.


K3) HOW TO CALCULATE
For each CP row, for each reporting column:
  calculated = sum of all member values (treating "-" as 0, parenthesized
               as negative, e.g. "(1,234)" = -1,234).
  For intermediate CP references: use that CP row's already-extracted
  reported value (do not re-sum its members recursively).


K4) WHAT TO DO WITH THE RESULT
For each CP row compute:
  status = PASS   if calculated == reported for ALL reporting columns
  status = FAIL   if calculated != reported for ANY reporting column

Add "Total Check Status" as a field on every CP row in the JSON output:
  PASS rows:     "Total Check Status": "PASS"
  FAIL rows:     "Total Check Status": "<ColName>: FAIL" for each failing column,
                 pipe-separated if multiple columns fail.
                 Example: "Total Check Status": "Governmental Activities: FAIL | Total: FAIL"
  DP and DPG rows: "Total Check Status": ""   (empty string, always)


K5) DO NOT REPAIR — REPORT ONLY
This check is diagnostic. Never alter any extracted value to make a check pass.
If a CP row fails, output it exactly as extracted and mark it FAIL.
The purpose is to surface extraction errors, not hide them.


K6) SKIPPED CHECKS
