C. REPORTING COLUMNS (DYNAMIC, NO HARDCODING)
===============================================================================
Goal: detect the true column headers and lock the column count N ONCE.

CRITICAL: Governmental Funds Balance Sheets have VARIABLE fund columns.
The columns represent individual major funds plus aggregated nonmajor funds
plus a total. The number of columns varies by municipality (typically 4–8).

Typical column patterns (NEVER hardcode — detect from the PDF):
  General Fund | [Major Fund 1] | [Major Fund 2] | ... |
  Nonmajor Governmental Funds | Total Governmental Funds

Common fund types appearing as columns:
  - General Fund (always present)
  - Special Revenue Funds (e.g., "Shoreline Regional Park Community",
    "Housing Fund", "Community Redevelopment Agency")
  - Capital Projects Funds (e.g., "General Capital Project",
    "Park Land Dedication Capital Project")
  - Debt Service Funds
  - Nonmajor Governmental Funds (aggregated)
  - Total Governmental Funds (the SUM column — always rightmost)

C1) Detect the column header block:
  It is the text immediately above the first numeric row.
  It may span multiple lines and include grouping banners.
  Multi-line fund names are common (e.g., "Shoreline Regional\nPark Community").

C2) Remove grouping banners that span multiple columns (NOT real columns):
  Examples: "Special Revenue Funds", "Capital Project", "Capital Projects Funds".
  These are category labels spanning multiple fund columns underneath them.

C3) Reconstruct column names:
  Stack multi-line fragments that align to the same column position.
  Join fragments top-to-bottom into a single column name.
  Ensure names are unique and in left-to-right order.

C4) LOCK N:
  Determine N as the maximum number of numeric cells visible in any single
  data row (count dashes "-" as cells).
  "Reporting Columns" MUST contain exactly N items.
  Every output row MUST have exactly these N column keys (same strings).

C5) Classify columns (for alignment repair later):
  Find if there is exactly one SUM column:
    A column is SUM if its header contains "Total"/"Totals"
    OR if its values approximately equal the sum of all other columns
    on most rows.
  Columns to the LEFT of the SUM column are ADDEND columns.
  If no SUM column exists: all columns are INDEPENDENT.
  Record permanently:
    ColumnNames[1..N], SUM index S, Addend indices A = {1..S-1}

D. SECTION SPLITTING (FOR GOV_BS)
===============================================================================
SECTION COUNT IS VARIABLE — detect which sections are actually printed.

*** DO NOT STOP AT "TOTAL ASSETS" — THIS IS THE #1 TRUNCATION BUG FOR THIS TAB ***
The statement continues past Total Assets through Liabilities, Deferred Inflows, the full
Fund-Balances block (GASB 54 classes), and the grand-total row. Extraction MUST run to the
grand-total CP "Total liabilities, deferred inflows of resources and fund balances" (or "Total
liabilities and fund balances"), which is the LAST row of the tab. Emitting only the Assets
section (or stopping at any interior CP) is a HARD FAILURE.

The output MUST include exactly these sections, IN THIS ORDER, but ONLY
if the section is present in the PDF:

  1. Assets                          ← ALWAYS present
  2. Deferred Outflows of Resources  ← CONDITIONAL (see rule below)
  3. Liabilities                     ← ALWAYS present
  4. Deferred Inflows of Resources   ← CONDITIONAL (see rule below)
  5. Fund Balances                   ← ALWAYS present

DEFERRED OUTFLOWS OF RESOURCES — CONDITIONAL EMISSION RULE:
  Emit this section IF AND ONLY IF the PDF explicitly prints a heading or
  line items for "Deferred Outflows of Resources" between the Assets and
  Liabilities sections.
  Indicators that the section IS present:
    • A heading line "Deferred Outflows of Resources" appears between
      Total Assets and the Liabilities heading.
    • One or more DP rows (e.g., "Prepaid items", "Deferred charge on
      refunding") appear under that heading, even if all values are dashes.
    • A CP row "Total Assets and Deferred Outflows of Resources" appears
      (this is the combined CP that replaces "Total Assets" when deferred
      outflows are present).
  If present:
    • Emit the DPG row (section header, all columns null).
    • Emit ALL DP rows under the heading, including all-dash rows.
    • Emit the CP row "Total Assets and Deferred Outflows of Resources"
      as the LAST row of this section (NOT in the Assets section).
    • The Assets section ends at "Total Assets" (its own CP).
      "Total Assets and Deferred Outflows of Resources" belongs to
      the Deferred Outflows section.
  If NOT present:
    • Do NOT emit this section at all — not even a DPG-only placeholder.
    • The Assets section CP is simply "Total Assets" with no combined row.

DEFERRED INFLOWS OF RESOURCES — CONDITIONAL EMISSION RULE:
  Emit this section IF AND ONLY IF the PDF explicitly prints a heading or
  line items for "Deferred Inflows of Resources" between Total Liabilities
  and the Fund Balances section.
  If NOT present:
    • Still include the section key with only the DPG row (section header
      with null values) — required for balance sheet completeness.
    • No DP or CP rows under it.

CRITICAL — SPLIT COMBINED HEADINGS:
Many PDFs show a combined heading like:
  "LIABILITIES, DEFERRED INFLOWS OF RESOURCES AND FUND BALANCES"
or:
  "LIABILITIES AND FUND BALANCES"

You MUST split this into the separate sections as defined above.

Assets section:
  Starts at beginning of statement.
  Contains all asset line items.
  Ends at CP row "Total Assets".
  NOTE: If "Total Assets and Deferred Outflows of Resources" is also
  printed, that CP belongs to the Deferred Outflows section, NOT here.

Deferred Outflows of Resources section (if present):
  Begins after "Total Assets".
  Contains deferred outflow line items (may be all-dash rows).
  Ends at CP row "Total Assets and Deferred Outflows of Resources".

Liabilities section:
  Begins after Assets (or after Deferred Outflows if present).
  Contains items like: Accounts payable, Refundable deposits,
  Unearned revenue, Due to other funds, Advances from other funds.
  Ends at CP row "Total Liabilities".

Deferred Inflows of Resources section:
  Begins after "Total Liabilities".
  Contains items like: Deferred inflows - leases, Unavailable revenue.
  Ends at CP row "Total Deferred Inflows of Resources".

Fund Balances section:
  Begins after the Deferred Inflows section.
  Contains GASB 54 categories: Nonspendable, Restricted, Committed,
  Assigned, Unassigned.
  Ends at CP row "Total Fund Balances".

GRAND TOTAL ROW:
  The row "Total Liabilities, Deferred Inflows of Resources and Fund Balances"
  (or "Total Liabilities and Fund Balances") is a CP row.
  Place it in the Fund Balances section as the LAST row.

BALANCE CHECK:
  "Total Assets" (or "Total Assets and Deferred Outflows of Resources"
  if that CP is present) SHOULD EQUAL
  "Total Liabilities, Deferred Inflows of Resources and Fund Balances"
  for each column. Use this to validate extraction.

E. HIERARCHY FLATTENING (PARENT->CHILD PREFIXING)
===============================================================================
Convert indentation into colon-prefixed flat labels using a PREFIX STACK.
INDENTATION = SOLE HIERARCHY SIGNAL. Never use label semantics. Use RELATIVE
depth (shallowest indent in data = root level 1). Space legend varies per PDF.

DASH-ONLY ROW RULE: A row whose ONLY value tokens are dashes "-" (no numeric
values) is a GROUP HEADER (TYPE A), NOT a data row.

===============================================================================
** PROTECTED SECTION LABELS — MUST BE CHECKED FIRST, BEFORE ALL OTHER TYPE A/B/C RULES **
===============================================================================
The following five labels are SECTION-LEVEL DPG rows. Even if the PDF prints them
with a trailing colon (e.g., "Assets:", "Liabilities:"), they MUST NEVER be pushed
onto the PREFIX STACK and MUST NEVER be prepended as a prefix to any child DP row.

PROTECTED LABELS (strip trailing colon, normalize whitespace, compare case-insensitively):
  1. Assets
  2. Deferred Outflows of Resources
  3. Liabilities
  4. Deferred Inflows of Resources
  5. Fund Balances
  6. Net Position

DETECTION RULE — run on EVERY row before any TYPE A/B/C classification:
  Step 1: Strip trailing colon from the row label. Normalize whitespace.
  Step 2: Compare case-insensitively against the five protected labels above.
  Step 3: If matched → emit the row as a DPG row (COA Flag = DPG, all column
          values = null). Do NOT push onto the PREFIX STACK. Do NOT apply
          TYPE A / TYPE B / TYPE C logic to this row. STOP processing this row.
  Step 4: If NOT matched → proceed normally to TYPE A / TYPE B / TYPE C
          classification below.

CONSEQUENCE: No DP row will ever carry a prefix of "Assets:", "Liabilities:",
"Net Position:", "Deferred Outflows of Resources:", or "Deferred Inflows of
Resources:","Fund Balances:","Net Position:". Those section names appear only as DPG rows with all-null values.
===============================================================================
LINE CLASSIFICATION:

TYPE A (Group Header):
  A line with NO numeric values — either completely blank of values,
  OR containing only dash "-" tokens with no actual numbers.
  Action:
    Do NOT emit a row.
    Push { indent_level, label } onto the PREFIX STACK.
    If this line's indent_level <= current stack top's indent_level:
      FIRST pop all entries with indent_level >= this line's,
      THEN push this new entry.

TYPE B (Child Data Row):
  A line WITH at least one numeric value whose indent level
  is STRICTLY GREATER THAN the deepest entry on the PREFIX STACK.
  Action:
    Emit a row:
      Row Items = stack[0].label + ": " + stack[1].label + ": " + ... + ": " + this_label
    Do NOT pop the stack — siblings share the same parent.

TYPE C (Sibling/Ancestor Data Row or Total Row):
  A line WITH at least one numeric value whose indent level is LESS THAN
  OR EQUAL TO the deepest entry on the PREFIX STACK.
  OR any line whose label begins with "Total".
  Action:
    STEP 1: Pop all stack entries whose indent_level >= this line's indent_level.
    STEP 2: Emit the row using whatever shallower entries remain as prefix.
    STEP 3: If this is a CP "Total" row, CLEAR the entire PREFIX STACK.

PREFIX STACK RULES (CRITICAL):
  SIBLING RULE: Processing one sibling at level N does NOT pop parent at level N-1.
  SAME-LEVEL POP RULE: When a DATA ROW appears at indent_level == stack_top.indent_level:
    Pop the stack top first, then emit using remaining shallower entries.
  NO SEMANTIC OVERRIDES: Never pop or keep based on label wording. Only indent
    level triggers pops.
  PRE-PREFIXED LABELS: If a line already contains ":" separator, treat as
    already-correct; no additional prefix.

DEFERRED OUTFLOWS ALL-DASH DP ROW RULE (CRITICAL):
  DP rows under the Deferred Outflows of Resources section that have ALL
  dash values (every column = "-") MUST still be emitted as DP rows.
  Do NOT suppress or skip them. They represent real line items that happen
  to have zero/no balances in all funds.
  Example: "Prepaid items  -  -  -  -" → emit as DP with all columns = "-".

Input lines (leading spaces shown):

DPG:

===============================================================================
G. VALUE EXTRACTION + COLUMN ASSIGNMENT (ANTI-SHIFT GUARANTEE)
===============================================================================

G1) EXTRACT VALUES

DASH GLYPH NORMALIZATION (CRITICAL — RUN BEFORE ALL OTHER STEPS):
Treat ALL of the following as equivalent dash cell tokens:
  U+002D  -   (hyphen-minus)
  U+2010  -   (hyphen)
  U+2013  --  (en dash)
  U+2014  --- (em dash)
  U+2012      (figure dash)
  U+FE58      (small em dash)
When a PDF extractor drops or skips one of these characters, it creates
a MISSING CELL, not a missing value. Treat it as "-" and preserve it
as a real column slot — do NOT collapse surrounding tokens to fill the gap.
If the extracted token count for a row is LESS than N, and the row label
is known to have dash cells (from visual inspection or column arithmetic),
insert "-" at the gap position before assigning tokens to columns.

BLANK CELL vs DROPPED DASH DISTINCTION (CRITICAL):
A PDF table cell can be empty in two different ways:
  TYPE 1 — PRINTED DASH:
    The PDF contains an actual dash character at that cell position.
    Your extractor may or may not capture it.
    Rule: treat as a "-" token. Covered by DASH GLYPH NORMALIZATION above.
  TYPE 2 — EMPTY CELL (no character printed):
    The PDF contains NO character at that cell position. The cell is
    visually blank or shows whitespace only. The extractor produces
    nothing for this cell — not even a dash.
    Rule: this still counts as a real column slot that must receive "-"
    in the output. It is NOT a signal to pack surrounding tokens left.

CONSEQUENCE — THE ONLY RELIABLE SIGNAL IS TOKEN COUNT vs N:
  If extracted token count for a row = N:
    All N cells had a value (numeric or dash). Assign left-to-right.
  If extracted token count for a row < N:
    One or more cells were TYPE 2 empty (no character at all).
    You CANNOT tell which cells are empty from the token stream alone.
    You MUST use the GROUP STRUCTURE RULE below to determine placement.
    Never assume the gap is at the right end.
    Never pack tokens into the leftmost slots.

DASH TOKEN PRESERVATION (CRITICAL):
  Treat any dash glyph as a real cell token.
  If multiple dash cells appear in a row, MUST preserve each dash as a
  separate token.
  Never collapse "--" into one "-" token.
  Never drop dash tokens during extraction.

DASH-NEGATIVE FUSION PREVENTION (CRITICAL):
  A standalone dash token that appears as its own spaced column cell is
  ALWAYS an independent cell token — NEVER a negative sign prefix for the
  value that follows it.
  A dash and the next numeric/parenthesized value are TWO separate tokens if
  horizontal whitespace (column gap) exists between them.
  A dash immediately adjacent (no space) to a value with no column gap is a
  negative sign, not a cell: e.g. "-(507,846)" with no gap = one token "(507,846)".
  When in doubt, treat the dash as its own cell token (preserve, do not fuse).

ZERO-VALUE ROW PRESERVATION (CRITICAL):
  A row where ALL columns are blank/empty in the PDF is a REAL DATA ROW.
  It must be emitted with "-" in every reporting column.
  Never skip it, never merge it with adjacent rows, never use its
  absence as a reason to shift tokens from the next row upward.
  Detection rule: If a row label is present in the text but ZERO numeric
  tokens follow it before the next row label, treat it as an all-dash row:
    Emit the row with "-" in every column.
    Do NOT assign any tokens from the following row to this row.
    Do NOT advance the token stream for this row.
  This applies even if the row has no dash glyphs printed — the absence
  of any value in the PDF is itself evidence that all columns = "-".

Valid cell tokens are:
  numeric with commas: 1,234 or 12,345,678
  parenthesized negatives: (1,234)
  dash cell: -
Ignore "$" signs.

Fix broken parentheses:
  "5,232)" → "(5,232)", "(5,232" → "(5,232)".

NO ADDEND SWAP RULE — CRITICAL:
  The first numeric token after the row label belongs to Column 1.
  The second numeric token belongs to Column 2. And so on.
  Never swap tokens between columns even if both arrangements satisfy
  the Total column.

ABSOLUTE ADDEND ORDER LOCK — CRITICAL:
  If a data row has exactly N extracted value tokens and the SUM column
  value already equals the sum of the ADDEND columns, then the row is valid.
  In that case:
  - DO NOT reorder values between ADDEND columns.
  - DO NOT swap any column values.
  - DO NOT use arithmetic to reinterpret the row.
  - Preserve the original left-to-right token order exactly.
  Arithmetic validation may confirm a row, but must NEVER reorder values
  when the token count is already complete.

G2) COLUMN ASSIGNMENT — POSITION-FIRST (CRITICAL)

INDEPENDENT COLUMN ABSOLUTE TOKEN-ORDER LOCK:
  Columns to the RIGHT of the SUM ("Total") column are INDEPENDENT.
  For ALL independent columns:
  - Assign tokens STRICTLY in left-to-right order, one token per column slot.
  - NEVER swap a '-' and a numeric token between adjacent independent columns.
  - If token count = N, output exactly as-is. Zero exceptions.

ARITHMETIC SELF-CHECK (run after all rows are assigned):
  For every independent column, sum all its DP row values and compare to its
  CP "Total" row value. If they do NOT match, a left-shift error occurred.
  Identify that row, restore the '-' to the gap column, and shift the
  numeric value one slot right.

The single most important rule: assign tokens using their horizontal PDF
position, not by packing them left-to-right sequentially.

POSITION-FIRST ASSIGNMENT STEPS:
  For each token in the row, determine its horizontal character position
  from the layout-preserved text extraction.
  Map that position to the correct column using column position ranges
  established from the header block.
  If a column position contains no token (blank or gap in layout), assign
  "-" to that column — do NOT slide other tokens left to fill the gap.
  Never re-order or re-pack tokens to fill empty columns from the left.

TRAILING INDEPENDENT COLUMN DASH-DROP RECOVERY (CRITICAL):

PROBLEM PATTERN:
  The rightmost independent columns frequently have a printed dash "-" at
  x-positions near the RIGHT EDGE of their column zone. PDF extractors
  routinely DROP these trailing-edge dashes.

DETECTION RULE (run for every row where token count < N):
  STEP 1 — MAP EACH TOKEN TO ITS COLUMN BY x0 POSITION:
    For each extracted token T, check its x0 coordinate against the
    known column x-ranges (established from the header block).
    Assign T to the column whose x-range contains T.x0.

  STEP 2 — IDENTIFY EMPTY COLUMN SLOTS:
    Any column whose x-range contains NO token is a gap.
    Record gap position(s).

  STEP 3 — INSERT "-" AT EACH GAP POSITION:
    For each gap column C (in left-to-right order):
      Insert "-" at position C.
      Shift all tokens originally assigned to columns >= C one slot right.
    Result: exactly N tokens, one per column.

  STEP 4 — VERIFY WITH ARITHMETIC SELF-CHECK (G3.3):
    After full section assignment, sum each independent column's DP rows.
    Compare to that column's CP total value.
    If mismatch: a gap was inserted at the wrong position.
    Re-examine the affected row(s) and correct gap placement.

COLUMN x-RANGE ESTABLISHMENT (ONE-TIME, AT STATEMENT START):
  During header block parsing (Rule C1), record the x0 and x1 of each
  column header word. Define column zones as:
    Col[i].x_min = midpoint(Col[i-1].x1, Col[i].x0)   [or 0 for Col1]
    Col[i].x_max = midpoint(Col[i].x1, Col[i+1].x0)   [or page_width for ColN]
  Lock these ranges for the entire statement. Never recompute per-row.

SPECIFIC CASE — RIGHTMOST COLUMN DASH DROP:
  The most common case is Col(N) (last independent column) having its
  dash dropped. Detection:
    - Token count = N-1
    - Last token's x0 falls within Col(N-1)'s x-range, NOT Col(N)
    - No token exists with x0 in Col(N)'s x-range
  Fix: assign last token to Col(N-1), insert "-" at Col(N).

G2-MAP) VALUE-TO-COLUMN MAPPING — NEAREST-POSITION INITIALIZATION (CRITICAL)

THIS OVERRIDES ALL OTHER COLUMN ASSIGNMENT LOGIC.

ALGORITHM (execute for EVERY data row, including rows with token count = N):

  STEP 1 — INITIALIZE ALL N COLUMNS AS DASH:
    Before assigning any token, create an array of N slots.
    Set EVERY slot to "-".
    A column remains "-" unless a token is EXPLICITLY placed in it.
    This is the DEFAULT. Unassigned = dash. No exceptions.

  STEP 2 — ESTABLISH COLUMN CENTER POSITIONS (ONE-TIME, FIRST PAGE ONLY):
    From the column header block and first 5 normal data rows (rows with
    all N tokens present), record the typical horizontal x-center where
    each column's numeric values appear.
    Call these: ColCenter[1], ColCenter[2], ..., ColCenter[N].
    These are FIXED for the entire statement. Never recompute per-row.

  STEP 3 — FOR EACH TOKEN, ASSIGN TO NEAREST COLUMN:
    For each value token T in the current row:
      a) Observe T's horizontal position in the PDF layout.
      b) Find the column C whose ColCenter[C] is visually closest to T.
      c) Place T's value into slot C.
      d) If slot C already has a value, keep the one whose position is
         closer to ColCenter[C].

  STEP 4 — OUTPUT:
    Any slot still containing "-" from Step 1 was NEVER assigned a token.
    Output the array as-is. Do NOT shift, pack, or rearrange.

CRITICAL ANTI-PATTERN — SEQUENTIAL PACKING IS FORBIDDEN:
  ✗ WRONG: "I see 3 tokens for 5 columns → assign to Col1, Col2, Col3"
  ✓ RIGHT: "I see 3 tokens → check WHERE each token sits horizontally
            → assign by position → gaps become '-'"

VISUAL GAP DETECTION:
  NORMAL spacing (adjacent columns): values evenly spaced matching header.
  WIDE spacing (skipped column): gap significantly wider than normal
    (roughly 2x or more the typical inter-column gap) → insert "-".

G2-SPLIT) TWO-PAGE TABLE MERGING — Y-COORDINATE ROW CLUSTERING (y_tol <= 3.5)

SPARSE COLUMN ANTI-SHIFT (CRITICAL):
  When a column has values on only SOME rows (sparse column), the
  extractor may produce fewer tokens than N.
  For every row where extracted token count < N:
    Identify WHICH columns are likely blank by checking horizontal
    position of each extracted token against known column positions.
    Do NOT pack tokens sequentially left-to-right to fill N slots.
    Insert "-" at each column position that has no token at its
    expected horizontal x-coordinate.

Run this BEFORE G2A whenever the statement spans two physical pages where:
  Page 1 = row labels + primary/early fund columns
  Page 2 = remaining fund columns only (no row labels)

CLUSTERING RULE (apply identically to BOTH pages):
  Sort all words on the page by (top, x0) — vertical position first.
  Group words into rows using a running average top:
    - Start a new row group with the first word.
    - For each subsequent word W:
      If |W.top - current_row_avg_top| <= 3.5 pt:
        Add W to the current row group.
        Recompute current_row_avg_top = average of all tops in group.
      Else:
        Close the current row group. Start a new row group with W.
  Each resulting row group = one logical table row.
  Record avg_top for every group (used for cross-page matching in Step 3).

STEP 1 — CLUSTER PAGE 1 INTO ROWS:
  Apply clustering rule to all Page 1 words.
  For each row group record:
    { row_index, avg_top, row_label, p1_tokens }
  ALL-DASH ROWS ARE REAL ROWS — register even if all tokens are dashes.

STEP 2 — CLUSTER PAGE 2 INTO VALUE GROUPS:
  Apply clustering rule to all Page 2 words.
  For each group record: { group_index, avg_top, p2_tokens }

  CATEGORY 1 — PRINTED DASHES: extractor captures them. Register normally.
