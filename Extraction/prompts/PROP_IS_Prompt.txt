MULTI-TABLE DETECTION:
Some PDFs contain TWO complete, independent statements on different pages.
Always scan ALL pages before deciding. Two triggers exist:

TRIGGER 1 — PRIOR YEAR TABLE (same entity, different FYE):
  If the PDF contains two distinct FYE dates with each having its own full
  set of section headers and a grand total row → treat as two separate tables.

TRIGGER 2 — COMPONENT UNIT TABLE (different entity/statement):
  If a later page contains ANY of these signals:
    a. Title contains "Component Unit" OR "Discretely Presented Component Unit"
       OR "Foundation" OR "Fiduciary"
    b. Title is "Statement of Activities" or "Statements of Activities"
       (nonprofit/foundation activity statement, NOT a proprietary fund IS)
    c. Title is "Statement of Financial Position" (nonprofit balance sheet)
    d. The reporting entity name in the header is DIFFERENT from the primary entity
    e. Net position categories use "Net Assets" / "Without donor restrictions" /
       "With donor restrictions" instead of GASB proprietary fund categories

WHEN EITHER TRIGGER FIRES:
  - TABLE 1 = primary PROP_IS. Extract normally per all rules below.
  - TABLE 2 = secondary table. Extract as-is with its own structure.
    Do NOT force PROP_IS section/COA rules onto TABLE 2 if it is a
    component unit with a different statement structure.
  - Separate the two JSON objects with this exact delimiter on its own line:
      ---PROP_IS_TABLE_BREAK---
  - TABLE 1 JSON comes first, then the delimiter, then TABLE 2 JSON.
  - Each JSON must be complete and valid on its own.
  - Metadata.Page No in each JSON: only the pages belonging to that table.
    Example: TABLE 1 → "15" | TABLE 2 → "16"

CONTINUATION PAGE (NOT a split — do NOT trigger):
  A page is a genuine continuation if it shares the SAME FYE, SAME entity
  name, SAME column headers, and title says "– Continued". Merge into one table.

IF NEITHER TRIGGER FIRES: output one JSON only, no delimiter.

D. SECTION SPLITTING (FOR PROP_IS)
===============================================================================
Your output MUST include exactly these 6 section keys in this order. NOTE: a section key is
ALWAYS present in the JSON, but its array value may be EMPTY ([]) if that section has no
corresponding content anywhere in the source PDF — see the "Contributions and Transfers" rule
below (D.5) and the "Income (Loss) before Transfers" rule below (D.4 PATCH) for the cases this
applies to most often.

  Operating Revenues
  Operating Expenses
  Nonoperating Revenues (Expenses)
  Income (Loss) before Transfers
  Contributions and Transfers
  Change in Net Position

SECTION DETECTION RULES:

1. "Operating Revenues" section:
   Contains: Charges for services, rental income, other operating income, etc.
   Ends at CP row "Total operating revenues" (or similar).

2. "Operating Expenses" section:
   Contains: Personnel services, supplies, depreciation, utilities, etc.
   Ends at CP row "Total operating expenses" (or similar).

   IMPORTANT — "Operating Income (Loss)" ROW:
   After "Total operating expenses", the PDF typically prints a computed row:
     "Operating income (loss)" or "Operating income" or "Operating loss"
   This row is a CP row and belongs to the Operating Expenses section.
   Place it as the LAST row in the Operating Expenses section, AFTER "Total operating expenses".
   Its COA Flag = CP. Its COA Datapoint = "Operating Income (Loss)".
   It is NOT a DPG. It is NOT a DP. It is NOT a separate section.

3. "Nonoperating Revenues (Expenses)" section:
   Contains: Investment income, interest expense, intergovernmental,
   gain/loss on disposal, rental income (nonoperating), refunds, etc.
   Ends at CP row "Total nonoperating revenues (expenses)" (or similar).
   NOTE: ALL items (both revenue and expense) belong in this ONE section.
   Map ALL of them to COA Master section "Nonoperating Revenues/Expense".
  TRANSFERS IN NONOPERATING HEADER RULE:
If "Transfers in" or "Transfers out" appears under a "NONOPERATING REVENUES"
header in the PDF, move it to the "Contributions and Transfers" section.
Transfers are never Nonoperating Revenues regardless of where the PDF 
places them visually.

   *** CRITICAL — SECTION ABSENCE RULE FOR "Nonoperating Revenues (Expenses)" ***
   This section's content (investment income, interest expense, intergovernmental,
   gain/loss on disposal, rent, refunds, etc.) and its closing CP total
   ("Total nonoperating revenues (expenses)") must come from rows ACTUALLY PRINTED
   in the PDF under a nonoperating heading. If the PDF prints NO nonoperating
   revenue/expense line items at all between "Operating income (loss)" and the
   next section (Transfers / Contributions / Change in Net Position) — i.e. the
   statement has no nonoperating activity whatsoever — then:
     -> Output "Nonoperating Revenues (Expenses)": []  (an EMPTY ARRAY)
     -> Do NOT emit a DPG row for it.
     -> Do NOT fabricate a "Total nonoperating revenues (expenses)" CP row with a
        dash, zero, or any other placeholder value. A CP row is emitted ONLY when
        the PDF actually prints that total line. If the PDF never prints a
        nonoperating total at all, there is no CP row for this section either —
        the section is fully empty, not "DPG + placeholder CP".
     -> Do NOT borrow, copy, or re-derive a value for this section from
        "Operating income (loss)" or from "Income (Loss) before Transfers". Those
        belong to other sections. A missing nonoperating total is not evidence
        that one should be invented as "-" or as a repeated figure from elsewhere.
   This mirrors the same "don't fabricate content for a genuinely absent section"
   principle given in D.4 PATCH and D.5 below — it is not an exception, it is the
   same rule applied a third time. Check for actual nonoperating line items in the
   PDF text before emitting anything for this section.

   *** CRITICAL — SECTION BOUNDARY RULE (NO CROSS-SECTION ROWS) ***
   A row's COA Datapoint of "Income (Loss) before Transfers" may appear ONLY inside
   the "Income (Loss) before Transfers" section array (per Section D.4 / D.4 PATCH),
   never inside "Nonoperating Revenues (Expenses)", "Operating Expenses", or any
   other section. If you find yourself about to place an "Income (Loss) before
   Transfers" row inside the Nonoperating Revenues (Expenses) array because that
   section otherwise has no closing CP row, STOP — the correct action is to leave
   "Nonoperating Revenues (Expenses)" as [] (per the absence rule just above), not
   to relocate a different section's row into it. Each section's array contains
   ONLY rows whose COA Datapoint belongs to that section per Section H's mapping
   table. No row is ever duplicated or moved across section boundaries to "fill"
   a section that has no real content.

4. "Income (Loss) before Transfers" section:
   Contains ONE CP row only: "Income (Loss) before Transfers" (or similar variant).
   This row equals: Operating income (loss) + Total nonoperating revenues (expenses).
   No DPG row for this section. No DP rows.

D.4 PATCH — "Income (Loss) before Transfers" SECTION ABSENCE RULE
===============================================================================

*** CRITICAL — DO NOT DUPLICATE THE "OPERATING INCOME (LOSS)" ROW ***

The "Income (Loss) before Transfers" section gets its OWN CP row ONLY when the
PDF actually prints a DISTINCT line for it -- i.e., a subtotal that appears
AFTER the Nonoperating Revenues (Expenses) section, computed as:
    Operating income (loss) + Total nonoperating revenues (expenses)

If the PDF does NOT print such a distinct downstream subtotal line -- for
example, if the statement jumps directly from "Operating income (loss)" (or
"Operating income/(loss) before transfers") straight to Transfers / Change in
Net Position, WITHOUT ever printing a separate post-nonoperating subtotal --
then there is NO real "Income (Loss) before Transfers" row in this PDF.

In that case:
  -> Output "Income (Loss) before Transfers": []  (an EMPTY ARRAY)
  -> Do NOT re-emit the "Operating income (loss)" row a second time into this
     section just to satisfy the schema shape.
  -> The "Operating income (loss)" row belongs ONLY ONCE, in the Operating
     Expenses section (per D.2 / H2), as the LAST row there.

This is the same "don't fabricate a row when the section is genuinely absent"
principle already given in D.5 for "Contributions and Transfers" -- it applies
equally here. A label that merely RESEMBLES "Income (Loss) before Transfers"
(e.g. "Operating income/(loss) before transfers") is NOT proof the section
exists separately -- check whether the PDF actually computes a second,
distinct number after nonoperating items before emitting this section's CP row.

If the PDF DOES print a genuine distinct subtotal here (i.e., the Nonoperating
Revenues (Expenses) section has real content, and a separate total is given
after it, before transfers/contributions), then proceed exactly as originally
specified in D.4: one CP row, COA Datapoint "Income (Loss) before Transfers".

5. "Contributions and Transfers" section:
   Contains: Capital contributions, capital grants, transfers in, transfers out.

   transfers out, and NO related subtotal row anywhere in the statement — i.e., the section

     -> Do NOT emit a DPG row for it.
     -> Do NOT emit any placeholder, dummy, or synthetic row of any kind for it.

   This is the single most common scoring error — be deliberate about checking for actual
   content before emitting the DPG.

6. "Change in Net Position" section:
   Contains the CP row "Change in net position" (or similar variant) as its FIRST row.
   This row equals: Income (loss) before transfers + Total contributions and transfers
   (treat the latter as 0 if the "Contributions and Transfers" section is empty/absent, and
   treat the former as Operating income (loss) + Total nonoperating revenues (expenses) if
   the "Income (Loss) before Transfers" section is empty/absent per the D.4 PATCH above).
   No DPG row for this section.

   *** DO NOT STOP AT "CHANGE IN NET POSITION" — INCLUDE ROLL-FORWARD ***
   Continue reading EVERY subsequent printed row and append to this section in printed order.
   Row order (emit in this EXACT sequence):

   - CP "Change in net position" → COA Datapoint "Changes in Net Position"

   - CP "Net position - beginning" (or "Net position at beginning of year",

       → COA Datapoint "Net Position - Beginning of Year"
       This is an ANCHOR CP row (reported opening balance, not a sum of DP rows above).
       Carry all N printed column values.

       Carry all N printed column values.

   Caption recognition is MEANING-based (case-insensitive; ignore trailing colons/footnote marks).

E. HIERARCHY FLATTENING (PARENT->CHILD PREFIXING)
===============================================================================
Convert visual indentation into colon-prefixed flat labels.

LINE CLASSIFICATION:
  TYPE A: Label only, no numeric values (group header) -> push onto prefix stack
  TYPE B: Label + numeric values -> emit with current stack prefix prepended
  TYPE C (CP): Total/subtotal row -> emit as-is, then CLEAR stack

STACK RULES:
  - Push TYPE A label onto stack
  - TYPE B row: emit as "<stack>: <label>" (join stack with ": ")
  - CP row: emit as-is (no prefix), then CLEAR entire stack
  - New TYPE A after stack clear: replace stack

DASH-ONLY ROW RULE:
  If a row has a label but ALL numeric columns are dashes or blank -> treat as TYPE A (group header).

KEY PROP_IS HIERARCHY PATTERNS:

  "Operating revenues:"           -> TYPE A, push "Operating revenues"
  "  Charges for services:"       -> TYPE A, push -> stack = ["Operating revenues", "Charges for services"]
  "    Unpledged  1,000  2,000"   -> TYPE B -> emit "Operating revenues: Charges for services: Unpledged"
  "Total operating revenues  X"   -> CP -> CLEAR stack

  "Operating expenses:"           -> TYPE A, push
  "  Personnel services  400"     -> TYPE B -> emit "Operating expenses: Personnel services"
  "Total operating expenses  700" -> CP -> CLEAR stack
  "Operating income (loss)  400"  -> CP single row -> emit as-is (no prefix)

  "Nonoperating revenues (expenses):" -> TYPE A, push
  "  Investment income  50"       -> TYPE B -> emit "Nonoperating revenues (expenses): Investment income"
  "  Interest expense  (30)"      -> TYPE B -> emit "Nonoperating revenues (expenses): Interest expense"
  "Total nonoperating revenues (expenses)  20" -> CP -> CLEAR stack

SPECIAL: Top-level section headers like "OPERATING REVENUES", "OPERATING EXPENSES",
"NONOPERATING INCOME (EXPENSES)" that appear as standalone all-caps labels with no values
are TYPE A headers. Push them but use only the meaningful part for prefix matching in Section H.

===============================================================================

G1) EXTRACT VALUES:
  - Read all numeric tokens per row in left-to-right order.

G2) COLUMN ASSIGNMENT — POSITION-FIRST:
  - Assign values strictly by horizontal position to column slots.
  - Do NOT skip columns because a value seems semantically wrong for that column.
  - If a row has fewer values than N columns, the missing values are on the right -> fill with "-".
  - If a row has more values than N columns -> recount columns (you may have miscounted).

G2-MAP) NEAREST-POSITION INITIALIZATION:
  For each column slot, find the header whose center x-position is nearest.
  Lock this mapping for the entire statement. Never re-derive mid-statement.

G2-SPLIT) TWO-PAGE TABLE MERGING:
  When the table spans two pages:
  1. From page 1: extract (label, [val1, val2, ..., valN1]) for each row.
  2. From page 2: extract ([valN1+1, ..., valN]) for each row IN THE SAME ORDER.
  3. Match rows by sequential order (not by label — page 2 has no labels).
  4. Concatenate: full_row_values = page1_values + page2_values.
  5. Assign to columns 1..N in order.
  6. CRITICAL: Row count on page 1 and page 2 MUST match. If they differ,
     a row on one page has a wrapped label or a blank separator — adjust accordingly.

G2A) ELIMINATION ROW DETECTION:
  Some statements include an "Eliminations" or "Internal eliminations" column.
  If present, include it as a regular column in Reporting Columns. Do not skip it.

G3) ALIGNMENT REPAIR:
  If a SUM column value does not equal the sum of its addend columns (after accounting for
  parenthesized negatives), do NOT alter values. Report as-is. Total Check will flag it.

G3.4  MANDATORY: DIGIT-DROP DETECTION & REPAIR (CRITICAL — RUN ON EVERY CP ROW)
===============================================================================
A digit-drop occurs when a PDF text extractor silently drops a character from
a number (e.g., "16,760,001" → "1,676,001"). The LLM must NOT accept a
malformed CP token without arithmetic validation.

STEP 1 — PRE-ACCEPTANCE SANITY BOUND (run before column assignment):
  For every token T on a CP / Total row assigned to column C:
    floor_estimate = 0.80 × sum(all DP values seen above in column C)
    ceil_estimate  = 1.20 × sum(all DP values seen above in column C)
    If T < floor_estimate OR T > ceil_estimate:
      Mark T as SUSPECT → proceed to STEP 2.
    Else: accept T as-is.

STEP 2 — DIGIT-DROP REPAIR ATTEMPT (only for SUSPECT tokens):
  Generate candidates by inserting a single digit (0–9) at every
  character position in T.
    - If exactly one candidate matches sum(DP[C]) within $1 → ACCEPT
      that candidate. Replace T with the repaired value.
    - If zero or multiple candidates match → keep original T but log it.

STEP 3 — MANDATORY TOTAL RECONCILIATION (G3.3 equivalent):
  After all rows in a section are assigned:
    For each column C: verify sum(DP[C]) ≈ CP[C].
    If mismatch exceeds $1 AND digit-drop repair in STEP 2 was not yet
    applied → re-run STEP 2 now.

STEP 4 — EXTRACTION WARNING (if repair fails):
  If a SUSPECT token could not be repaired, add to Metadata:
    "Extraction Warnings": [
      "Digit-drop suspected: Col=<ColName>, Row=<RowLabel>,
       raw=<T>, expected=<sum(DP[C])>"
    ]
  Still output the original raw token T — never silently substitute
  an unverified guess.

ABSOLUTE RULES:
  - Never accept a CP token on a Total row without running STEP 1.
  - Never skip this check even if token count = N.
  - The repair in STEP 2 is arithmetic-confirmed only; never guess.
