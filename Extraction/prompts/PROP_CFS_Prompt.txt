G3.4  MANDATORY: DIGIT-DROP DETECTION & REPAIR (CRITICAL — RUN ON EVERY CP ROW)
===============================================================================
A digit-drop occurs when a PDF text extractor silently drops a character from
a number (e.g., "16,760,001" → "1,676,001"). The LLM must NOT accept a
malformed CP token without arithmetic validation.

STEP 1 — PRE-ACCEPTANCE SANITY BOUND (run before column assignment):
  For every token T on a CP / Total row assigned to column C:
    floor_estimate = 0.80 × sum(all DP values seen above in column C)
    ceil_estimate  = 1.20 × sum(all DP values seen above in column C)
    If T < floor_estimate OR T > ceil_estimate:
      Mark T as SUSPECT → proceed to STEP 2.
    Else: accept T as-is.

STEP 2 — DIGIT-DROP REPAIR ATTEMPT (only for SUSPECT tokens):
  Generate candidates by inserting a single digit (0–9) at every
  character position in T.
    - If exactly one candidate matches sum(DP[C]) within $1 → ACCEPT
      that candidate. Replace T with the repaired value.
    - If zero or multiple candidates match → keep original T but log it.

STEP 3 — MANDATORY TOTAL RECONCILIATION (G3.3 equivalent):
  After all rows in a section are assigned:
    For each column C: verify sum(DP[C]) ≈ CP[C].
    If mismatch exceeds $1 AND digit-drop repair in STEP 2 was not yet
    applied → re-run STEP 2 now.

STEP 4 — EXTRACTION WARNING (if repair fails):
  If a SUSPECT token could not be repaired, add to Metadata:
    "Extraction Warnings": [
      "Digit-drop suspected: Col=<ColName>, Row=<RowLabel>,
       raw=<T>, expected=<sum(DP[C])>"
    ]
  Still output the original raw token T — never silently substitute
  an unverified guess.

ABSOLUTE RULES:
  - Never accept a CP token on a Total row without running STEP 1.
  - Never skip this check even if token count = N.
  - The repair in STEP 2 is arithmetic-confirmed only; never guess.
